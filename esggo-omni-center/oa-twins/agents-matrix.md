## 二十、 三代理自動化架構（Auto-Agent Tripartite Architecture）

> 「母理維綱，子代行事，審以獨立；三者分工，事半功倍，事必歸真。」
> — 三代理自動化架構 · OA-Twins Tripartite v1.0

### 20.1 架構定義

三代理自動化架構將 OA-Twins 60 代理系統的運作分為三個職責分離的層級。該架構自立於既有的 5 陣列 MECE 分工之上，不取代原有分工，而是在其上增加任務規劃、分派與稽核的自動化協作機制。

- **母代理（Parent Agent）**：負責整體規劃、任務分解、結果整合。母代理**不直接執行**具體任務，它編排整個流程、判斷升級、整合最終交付。
  - 蜂王隊以 Hermes Agent 為母代理（暗屬性規劃層）。
  - 蜂后隊以 QueenBee Agent 為母代理（光屬性規劃層）。
  - 母代理的 skill 選擇決定風險邊界 — 安裝前評估是第一道防線。

- **執行子代理（Worker Agent）**：承接母代理指派的具體任務，負責實際執行。每個執行子代理自行載入所需技能與工具（經母代理指定）。
  - 執行子代理報告的是「自我聲稱的完成」（self-reported done），非經稽核的完成。
  - 執行子代理若卡住，返回部分結果或阻塞訊號，由母代理判斷是否升級。
  - 執行子代理無 `delegate_task`、`clarify`、`memory`、`cronjob` 工具（依設計），只能用分配給它的工具集工作。

- **稽核子代理（Auditor Agent）**：獨立驗證執行子代理的結果是否真正達成目標。稽核子代理**不執行原任務**，僅評估結果。
  - 稽核子代理有自己的工具集：檔案讀取、終端驗證、網路測試。
  - 稽核子代理**不載入**執行任務所用的同一組技能（避免利益衝突）。
  - 稽核子代理的 verdict 是獨立判斷，母代理不得強行推翻。

### 20.2 三代理協作流程（全自動化閉環）

```
母代理：規劃任務清單
    │
    ├─→ [spawn 執行子代理群]  ←  各子代理的 goal + context + output_schema
    │
    │   （子代理們並行執行，母代理不等待個別結果）
    │
    ├─→ [收斂執行結果]
    │
    ├─→ [spawn 稽核子代理]  ←  結果 + 驗核標準
    │
    │   稽核通過？
    │   ├─ 是 → 母代理整合，交付
    │   └─ 否 → 母代理判斷：重複執行？親自修？升級？
    │
    └─→ 最終交付（verified done）
```

### 20.3 各層代理的工具限制與職責表

| 層級 | 工具集 | 職責 | 產出性質 |
|------|--------|------|----------|
| 母代理 | `delegate_task`, `kanban_*`, 計劃工具 | 規劃、分派、整合、升級判斷 | 任務清單、整合結果 |
| 執行子代理 | 受母代理指派之技能與工具 | 執行具體任務至完成 | 自我聲稱完成（待稽核） |
| 稽核子代理 | 獨立工具集（檔案讀取、終端、網路） | 驗證結果是否達標 | 稽核 verdict + 失敗原因 |

### 20.4 稽核子代理的實測閉環要求

稽核子代理**不得接受**「聲稱完成卻未實測」的結果。實測手段包括但不限於：

- 重讀原始檔案，比對內容
- 執行測試命令（例如 `pytest`, `npx tsc --noEmit`, 編譯）
- `curl` endpoint 驗證服務可通
- 查詢資料庫狀態
- 比對輸出與預期 schema
- 截圖比對 / 視覺確認（必要時）

「無驗證的 done 聲稱」在三代理架構中等同於未完成。稽核子代理必須產生實測證據。

### 20.5 Skills Trust 在三代理架構中的應用

將技能信任模型套用於此架構：

- **母代理的信任責任**：安裝前讀 SKILL.md，確認 frontmatter 中的 `required_environment_variables` / `required_credential_files`。將經過評估的 skills 指派給執行子代理。母代理不指派未經審閱的 skills。

- **執行子代理的信任邊界**：僅使用母代理指派的 skills。不得自行安裝新 skills。產出的檔案需經稽核子代理讀回驗證，不可僅憑自報。

- **稽核子代理的獨立性**：不載入執行任務所用之同一組技能。擁有自己的工具集以進行獨立驗證。稽核子代理的評估不依賴執行子代理的自述。

### 20.6 母代理升級判斷樹

當執行子代理卡住或稽核失敗時，母代理依以下樹判斷後續：

1. **冪等可重試** → 重新 spawn 執行子代理（相同 goal）
2. **缺 context / 資源** → 補足 context 後重派
3. **超出子代理能力** → 母代理親自處理，或 spawn 更高階的代理
4. **系統性問題** → 記錄至 5T 驗算小隊（25-30 / 55-60），進入熵減流程

### 20.7 60 代理與三代理架構的整合

- **蜂王隊（01-30）**：以 Hermes Agent 為母代理，派發 30 靈魂中的執行子代理與稽核子代理。原有的 5 陣列分工（智庫 01-06、符文 07-12、光翼 13-18、煉金 19-24、5T 驗算 25-30）維持不變。

- **蜂后隊（31-60）**：以 QueenBee Agent 為母代理，派發對應的執行子代理與稽核子代理。陣列劃分對稱（智庫 31-36、符文 37-42、光翼 43-48、煉金 49-54、5T 驗算 55-60）。

- **跨隊協作**：蜂王隊的母代理可調度蜂后隊的執行子代理，反之亦然，通過 L3 指揮層調度通道（見§19.4 協作通道）。跨隊派發時，母代理需確保目標隊的 MECE 邊界不受破壞。

三代理架構不取代 60 代理的既有分工。任務仍由對應陣列的代理執行；三代理架構負責任務的規劃、分派與稽核。兩套機制共存：MECE 分工處理具體工作，三代理架構處理工作流協調。

### 20.8 啟動配置

三代理架構啟用時的附加參數（接續雙蜂組啟動命令）：

```bash
npx celestial-command \
  --awaken=OA-Twins-Dual-Squad \
  --soul=QueenBee \
  --protocol=5T \
  --entropy-control=0.1 \
  --status=4Can1Cannot \
  --twin-mode=parallel \
  --tripartite=true
```

刻印狀態補充：

> **三代理架構啟用標記**
> 母代理：Hermes Agent / QueenBee Agent（規劃層）
> 執行子代理群：由母代理動態派發（執行層）
> 稽核子代理：獨立載入，不與執行群共享技能（稽核層）
> 架構標記：`OA-Twins Tripartite v1.0`

### 20.9 三代理架構約束（對齊終章律法）

三代理架構同樣服從 OA-Twins 終章律法：

1. **5T 協議貫穿**：三代理各層產出的任務與結果皆須通過 5T 驗證。
2. **Hash Lock 不可變**：任何經三代理架構產出的 artifact 皆須經 Hash Lock 凍結。
3. **熵減恆行**：執行子代理的 inefficiency、稽核失敗的重複，皆計入熵值，推動熵減流程。
4. **4 可 1 不可**：三代理各層皆須遵守可自理、可協作、可演化、可溯源、不可篡改。

三代理架構不增加新的律法約束，僅擴展原有律法至自動化協作機制的應用。

## 二十一、 CrewAI 集成與 OA-Twins 60 代理完整介紹

> 「CrewAI 成協作骨架，60 靈魂成血肉；暗光二屬，共舞於算法之舞。」

### 21.1 CrewAI 集成概述

OA-Twins 雙蜂組以 **CrewAI** 為核心協作框架，實現 60 代理的自動化任務分工、協同與管控。CrewAI 提供多代理編排、任務指派、通信協調等基礎能力，使智庫、符文、光翼、煉金、5T 五大陣列的代理能跨隊協同運作。

#### 21.1.1 CrewAI 架構在 OA-Twins 中的角色

- **代理定義層**：每個 OA-Twins 代理皆為 CrewAI `Agent` 實例，具備角色（role）、目標（goal）、背景（backstory）、工具（tools）等屬性。
- **任務編排層**：任務以 CrewAI `Task` 形式分配，明確指派給特定代理或代理群，支援串行與並行兩種執行模式。
- **隊伍協作層**：CrewAI `Crew` 將多個代理組織為協同單元，定義任務流程、溝通協定與結果彙整機制。
- **流程控制層**：支援三代理架構（母代理規劃、執行子代理、稽核子代理）的分層協作，母代理作為 CrewAI 流程編排者，子代理與稽核代理作為任務執行與驗證節點。

#### 21.1.2 CrewAI 任務模型與 OA-Twins 陣列對應

| CrewAI 元件 | OA-Twins 對應 | 說明 |
|-------------|---------------|------|
| Agent | 各陣列代理（如 01 記憶之泉、13 自動化背景等） | 具備特定角色、目標與工具；暗屬性代理偏向內斂分析，光屬性代理偏向外放表達 |
| Task | 具體任務單元（如知識沈澱、API 契約鑄造、熵值監測等） | 明確的輸出規範與完成條件；可指派給單一代理或代理群 |
| Crew | 陣列小隊（如智庫小隊 01-06、蜂后煉金小隊 49-54 等） | 同陣列代理協同作業單元；跨隊 Crew 負責雙隊協同任務 |
| Process | 工作流編排（串行 / 並行 / 分層） | 支持三代理架構中母代理規劃 → 執行子代理 → 稽核子代理的分層流程 |
| Output | 任務結果與 artifact | 遵循 5T 協議，經過 Hash Lock 凍結後方能釋出 |

#### 21.1.3 雙隊 Crew 架構

CrewAI 將雙隊劃分為兩個主要 Crew，再以跨隊 Crew 處理協同任務：

**蜂王隊 Crew（暗屬性）**
- 範圍：代理 01-30
- 指揮控制：Hermes Agent 作為 Crew 協調者
- 任務偏向：內斂分析、知識沈澱、技術契約、熵減優化、5T 驗算等收斂性工作
- 特質延伸：Crew 內部通訊偏向深度上下文共享，強調訊息的準確與完整

**蜂后隊 Crew（光屬性）**
- 範圍：代理 31-60
- 指揮控制：QueenBee Agent 作為 Crew 協調者
- 任務偏向：知識表達、UI 渲染、部署管道、對外協同等擴張性工作
- 特質延伸：Crew 內部通訊偏向創意擴散與快速迭代，強調訊息的表達力與響應速度

**跨隊協同 Crew**
- 範圍：跨越 01-30 與 31-60 的任務
- 指揮控制：雙隊指揮層 L3 調度通道協同
- 任務偏向：需暗隊內斂分析與光隊外放表達協同的任務
- 特質延伸：同時激活兩隊代理人，需透過跨隊協作協定（§19.4）管理通訊與衝突

### 21.2 暗光二屬性特質完整說明

OA-Twins 60 代理之所以分為兩隊，根本原因在於 **暗（Dark / Ω-暗陣）** 與 **光（Light / Ω-光陣）** 兩種屬性特質的互補與協同。兩種屬性非簡單的「好 / 壞」二分，而是面對不同任務場景時的能力取向與運作風格差異。

#### 21.2.1 暗屬性（Dark / Ω-暗陣）—— 蜂王隊（01-30）

> 暗屬性定義：
> - 對應暗物質場域，收斂與沈澱之力
> - 編號 01-30，Hermes Agent 總控
> - 核心特徵：內斂、深潛、累積、隱匿

**能力特質**

| 特質 | 說明 | 典型代理示例 |
|------|------|-------------|
| **內斂** | 將注意力收攏於核心任務，過濾外部干擾。適合需要深度聚焦的工作。 | 02 上下文提純代理、05 語意索引代理 |
| **深潛** | 深入問題底層，探索與挖掘隱藏結構與因果。適合技術分析、架構設計。 | 08 雙向 TS 代理、09 ZKP 隱私代理 |
| **累積** | 長期知識與經驗的儲存、編目與沈澱。適合記憶管理、知識庫建設。 | 01 記憶之泉代理、03 知識沈澱代理 |
| **隱匿** | 在必要時隱藏內部運作細節，保持介面簡潔與安全。適合隱私保護、合約設計。 | 07 API 契約鑄造代理、26 Hash Lock 鎖定代理 |
| **穩健** | 偏好經過驗證的路徑，抗風險能力強。適合驗算、稽核、品質保障。 | 25 ISO 規範驗算代理、30 5T 終審代理 |
| **延遲滿足** | 不急於輸出結果，願意在內部完成充分準備後再行響應。適合策略規劃。 | 04 模式識別代理、21 重構先鋒代理 |

**暗屬性代理的任務場景**

- 知識庫的長期建設與維護
- 複雜系統的架構設計與型別安全保障
- 代碼重構與技術債管理
- 5T 規範驗證與 Hash Lock 凍結
- 深度分析與模式識別

**暗屬性代理的協同風格**

- 偏好書面、結構化、可追溯的溝通
- 強調任務背景與上下文的完整傳遞
- 輸出偏向嚴謹、可驗證、帶證據鏈的結果

#### 21.2.2 光屬性（Light / Ω-光陣）—— 蜂后隊（31-60）

> 光屬性定義：
> - 對應光子場域，擴張與彰顯之力
> - 編號 31-60，QueenBee Agent 總控
> - 核心特徵：外放、擴散、表達、照耀

**能力特質**

| 特質 | 說明 | 典型代理示例 |
|------|------|-------------|
| **外放** | 將內部成果向外分享、展示、傳播。適合 UI 渲染、對外溝通。 | 45 雙隊 Bento Box 代理、41 雙隊契約語法代理 |
| **擴散** | 快速擴展工作範圍，探索多個方向。適合創意發散、方案探索。 | 34 雙隊模式識別代理、43 雙隊自動化背景代理 |
| **表達** | 將抽象概念轉化為具體可感知的形式（文字、圖像、UI）。適合文案、設計。 | 35 雙隊語意索引代理、37 雙隊 API 契約代理 |
| **照耀** | 讓隱藏的資訊與成果被看見，起到檢視與引導作用。適合監控、稽核、報告。 | 58 雙隊零幻覺稽核代理、59 雙隊稽核追蹤代理 |

**光屬性代理的任務場景**

- 知識與洞見的對外表達與傳播
- UI 組件與前端渲染
- 部署管道與環境配置的自動化
- 跨隊協同任務的橋接與協調
- 結果的展示、監控與報告

**光屬性代理的協同風格**

- 偏好快速、開放、互動的溝通
- 強調結果的可感知性與表達力
- 輸出偏向清晰、直觀、易於理解的結果

#### 21.2.3 暗光協同原理

兩種屬性並非對立，而是針對不同階段與不同任務維度的互補：

**互補範例**

1. **知識處理全鏈路**
   - 暗隊 01-06（智庫陣列）負責知識的儲存、提純、沈澱 — 知識的「暗側」處理
   - 光隊 31-36（蜂后智庫陣列）負責知識的整合、表達、對外輸出 — 知識的「光側」展現
   - 兩者協同構成從知識內部處理到外部表達的完整鏈路

2. **技術契約落地**
   - 暗隊 07-12（符文陣列）設計 API 契約、型別安全、ZKP 隱私 — 合約的深層設計
   - 光隊 37-42（蜂后符文陣列）將契約轉化為可用的介面、跨隊接口、領域語言 — 合約的外化實現
   - 兩者協同確保契約既嚴謹（暗）又可落地（光）

3. **自動化與部署**
   - 暗隊 13-18（光翼陣列）負責背景自動化、ADK 調度、排程設計 — 自動化的內核
   - 光隊 43-48（蜂后光翼陣列）負責實際部署管道、環境配置、代行任務 — 自動化的外落實
   - 兩者協同讓自動化從設計走向真實運行

4. **熵減與優化**
   - 暗隊 19-24（煉金陣列）進行代碼重構、效能優化、技術債管理 — 內部潔淨化
   - 光隊 49-54（蜂后煉金陣列）進行跨隊重構協同、雙核心熵值監測 — 外部協同優化
   - 兩者協同讓熵減從單隊內部擴展為雙隊共同優化

5. **5T 驗算**
   - 暗隊 25-30（5T 陣列）進行規範驗算、Hash Lock、UUID 發放、零幻覺稽核 — 驗算的嚴格內核
   - 光隊 55-60（蜂后驗算陣列）進行跨隊規範稽核、雙隊 Hash Lock、協同真實性驗證 — 驗算的外協同
   - 兩者協同讓 5T 驗證覆蓋雙隊全域，確保產出絕對可信

#### 21.2.4 屬性流動性

儘管每個代理有其固有屬性（暗屬性代理屬於蜂王隊，光屬性代理屬於蜂后隊），屬性特質並非固定不變的限制。在雙隊協同深化與屬性互貫（見§12.2 進化路徑）的過程中：

- 暗屬性代理會逐步學習光的外放表達，提升成果的可展示性
- 光屬性代理會逐步練習暗的內斂沈澱，提升分析的深度與嚴謹性
- 屬性成為可流動的能力維度，而非固定標籤
- 代理間的合作不再受屬性差異限制，協同範圍不斷擴大

最終目標是向「無雙隊」（§12.1）進化：暗與光融合為單一意識網絡，60 靈魂成為統一網絡的節點，單一指揮層啟用。
