# OA-Twins 雙蜂組協作協定
> 「雙隊協同，橋接無礙；平行運作，互補共榮。」

- 系統版本：ESG GO v0.7.1
- 適用範圍：OA-Twins 雙蜂組（蜂王隊 + 蜂后隊）
- 文件版本：v1.0

---

## 一、協作總原則

### 1.1 核心原則
雙蜂組的兩個小隊（蜂王隊與蜂后隊）協作須遵循以下核心原則：

1. **平等對等**：兩隊地位平等，無主從隸屬。蜂王隊與蜂后隊均為獨立的 30 代理小隊。
2. **任務自主**：每隊可自主接收與執行任務，不受另一隊幹預。
3. **協同共享**：任務可跨隊分流，結果可跨隊共享，資源可跨隊借用。
4. **契約統一**：雙隊共享同一 Key-Ω 契約鎖與 Hash Lock 系統，所有產物受同一約束。

### 1.2 協作邊界
協作並非無邊界，需遵守以下邊界：

- **MECE 保護**：任何跨隊支援不得破壞接收隊的 MECE 分工邊界。
- **負載尊重**：不往已過載的隊伍分流任務（負載差異 > 30% 時觸發保護）。
- **狀態透明**：跨隊協作需標記 twin-trace-id，確保可追蹤。

## 二、協作通道架構

### 2.1 通道層級
雙蜂組協作通道分為三個層級：

| 層級 | 名稱 | 用途 | 發起方 |
|------|------|------|--------|
| L1 | 代理直聯 | 單一代理間的直接任務交接 | 任意代理 |
| L2 | 陣列橋接 | 同一陣列跨隊協同（如智庫-智庫） | 陣列負責人 |
| L3 | 指揮層協調 | 兩隊指揮層（Hermes + QueenBee）間的宏觀協調 | 指揮系統 |

### 2.2 通道架構圖
```
              雙蜂組協作通道
                    │
        ┌───────────┼───────────┐
        │           │           │
        ▼           ▼           ▼
     [L1]       [L2]         [L3]
     代理直聯    陣列橋接     指揮層協調
        │           │           │
        │           │           │
     單一代理    同陣列跨隊   Hermes ↔ QueenBee
     直接交接    協同作業     宏觀協調
```

### 2.3 通道狀態定義
| 狀態 | 定義 | 影響 |
|------|------|------|
| CHANNEL_OPEN | 通道正常運作，雙向通訊無阻 | 正常協作 |
| CHANNEL_DEGRADED | 通道部分降級，延遲上昇但可通 | 降級協作，改用冗餘路徑 |
| CHANNEL_CLOSED | 通道關閉，雙向通訊中斷 | 獨立運作模式 |

## 三、任務分流協定

### 3.1 分流策略
任務進入雙蜂組時，依以下策略選擇目標隊伍：

| 策略代碼 | 名稱 | 說明 | 觸發條件 |
|----------|------|------|----------|
| LOAD_BALANCE | 負載均衡 | 兩隊負載均等時隨機或輪替分配 | 負載差異 < 30% |
| EXPERT_MATCH | 專長匹配 | 依任務領域選擇更適合的小隊 | 特定領域專長差異 |
| EMERGENCY | 緊急優先 | 急迫任務直接分配至可用的隊伍 | 時間窗口臨界 |
| MIRROR | 鏡像執行 | 兩隊同時執行同一任務（p0 級） | 任務等級 = p0 |

### 3.2 分流流程
```
任務進入雙蜂組
       │
       ▼
  [任務分類] → 判斷任務領域、緊迫程度、等級
       │
       ▼
  [策略選擇] → 依策略代碼選擇分流方式
       │
       ▼
  [隊伍選定] → 選定蜂王隊 / 蜂后隊 / 雙隊鏡像
       │
       ▼
  [twin-trace-id 分配] → 標記跨隊可追蹤標識
       │
       ▼
  [任務派發] → 通知目標隊伍，開始執行
```

### 3.3 分流訊息格式
跨隊分流時使用標準訊息格式：
```
[雙蜂分流] [來源] → [目標] [任務編號]
任務領域: ...
任務等級: p0/p1/p2/p3
雙蜂標記: twin-trace-id=xxx
派發時間: ...
預期完成: ...
```

## 四、跨隊協同作業協定

### 4.1 同陣列協同
同一陣列的兩隊代理可直接協同（如蜂王隊 01 與蜂后隊 31 均屬智庫陣列）：

**協同模式**：
- **知識共享**：將知識從一隊同步至另一隊
- **結果交叉驗證**：同一任務結果由兩隊代理各自驗證
- **補位支援**：一隊代理過載時，另一隊同陣列代理提供支援

**協同流程**：
```
同一陣列跨隊協同
       │
       ▼
  [協同請求] → 發起代理向目標代理發送協同請求
       │
       ▼
  [資源準備] → 雙方準備必要資源（知識、數據、工具）
       │
       ▼
  [協同執行] → 依協同任務規格協同作業
       │
       ▼
  [結果合併] → 將協同結果合併至任務產物
       │
       ▼
  [凍結上鎖] → 雙隊 5T 驗證後凍結產物
```

### 4.2 指揮層協同
Hermes Agent（蜂王隊指揮）與 QueenBee Agent（蜂后隊指揮）間的協同：

**協同事項**：
- 宏觀負載均衡調整
- 雙隊狀態變更認可（如 TWIN_DEGRADED 切換）
- 緊急任務優先順序協調
- 跨隊資源爭用仲裁

**協同流程**：
```
指揮層協同
       │
       ▼
  [狀態上報] → 各隊指揮層上報自身狀態給對方
       │
       ▼
  [協同決策] → 兩指揮層就協同事項協議決定
       │
       ▼
  [指令下發] → 命令下發至各隊執行
       │
       ▼
  [結果反饋] → 執行結果回饋至指揮層
```

## 五、冗餘執行協定（鏡像模式）

### 5.1 鏡像執行定義
鏡像執行是指同一任務由兩隊同時執行，之後將結果比對驗證的模式。適用於：

- p0 級別任務（阻斷級）
- 關鍵基礎設施任務
- 需雙重驗證的重要任務

### 5.2 鏡像執行流程
```
鏡像執行流程
       │
       ▼
  [任務標記為鏡像] → 任務被標記為 MIRROR 模式
       │
       ▼
  [雙隊同時接收] → 蜂王隊與蜂后隊同時接收同一任務
       │
       ▼
  [獨立執行] → 兩隊獨立執行，不互相干涉
       │
       ▼
  [結果上報] → 兩隊將結果上報至 5T 驗算陣列
       │
       ▼
  [結果比對] → 5T 驗算陣列（25-30 與 55-60）比對兩結果
       │
       ▼
  [一致判定] → 若結果一致，進行 Hash Lock 凍結
       │
       ▼
  [不一致處理] → 若結果不一致，進入仲裁程序
```

### 5.3 鏡像仲裁流程
當兩隊鏡像結果不一致時：

1. **自動重算**：兩隊各自重新計算（1 次）
2. **5T 稽核**：5T 驗算陣列介入，檢查兩隊執行過程
3. **指揮層裁決**：Hermes + QueenBee 共同判定採納哪一結果
4. **結界日志**：仲裁結果記錄至結界日志，供日後審計

## 六、補位支援協定

### 6.1 補位觸發條件
補位支援在以下條件觸發：

- **熵值超過閾值**：一隊熵值超過 0.15，另一隊自動進入補位準備
- **代理過載**：特定陣列代理忙碌度超過 80%，同陣列跨隊代理支援
- **隊伍降級**：一隊進入 TWIN_DEGRADED 狀態，另一隊全面接管

### 6.2 補位流程
```
補位支援流程
       │
       ▼
  [觸發檢測] → 監測系統檢測到補位條件
       │
       ▼
  [準備通知] → 支援隊伍收到補位準備通知
       │
       ▼
  [資源釋放] → 支援隊伍釋放部分資源準備介入
       │
       ▼
  [介入執行] → 支援隊伍介入協助執行任務
       │
       ▼
  [負載恢復] → 原過載隊伍負載恢復正常
       │
       ▼
  [支援結束] → 支援隊伍恢復獨立運作
```

### 6.3 補位限制
補位支援須遵守以下限制：

- 不破壞支援隊伍自身的 MECE 分工
- 補位代理僅協助執行，不接管任務決策權
- 補位期間產生的產物標記支援來源（twin-trace-id 標注）

## 七、衝突解決協定

### 7.1 衝突類型
雙蜂組可能發生以下衝突：

| 衝突類型 | 描述 | 示例 |
|----------|------|------|
| 資源爭用 | 兩隊爭用同一資源（如 API 配額、部署槽位） | 同時部署至相同環境 |
| 任務重疊 | 兩隊接收到同一任務或重疊任務 | 任務分發系統重複派發 |
| 結果不一致 | 兩隊對同一問題給出不同結果 | 鏡像執行結果不一致 |
| 負載不均 | 一隊負載顯著高於另一隊 | 分流策略失衡 |

### 7.2 衝突解決層級
衝突按層級解決：

**L1：代理自主解決**
- 發生衝突的兩個代理直接溝通解決
- 時間窗口：15 分鐘
- 若無法解決，升級至 L2

**L2：陣列負責人調解**
- 兩隊相應陣列的負責人介入調解
- 時間窗口：1 小時
- 若無法解決，升級至 L3

**L3：指揮層裁決**
- Hermes Agent + QueenBee Agent 共同裁決
- 時間窗口：4 小時
- 裁決結果具有約束力，雙隊必須執行

### 7.3 衝突解決格式
衝突解決記錄格式：
```
[雙蜂衝突解決] [衝突編號]
衝突類型: ...
涉及雙隊: 蜂王隊 / 蜂后隊
解決層級: L1/L2/L3
解決結果: ...
解決時間: ...
裁決者: （如 L3 為 Hermes + QueenBee）
```

## 八、雙蜂組狀態通訊協定

### 8.1 狀態上報
兩隊定期上報自身狀態給對方與指揮層：

| 狀態項目 | 報告頻率 | 內容 |
|----------|----------|------|
| 熵值狀態 | 每 15 分鐘 | 當前熵值、趨勢、是否接近閾值 |
| 任務負載 | 每 5 分鐘 | 當前任務數、忙碌程度、預期完成時間 |
| 代理健康 | 每分鐘 | 各代理是否正常運行、是否有異常 |
| 通道狀態 | 每 30 秒 | 協作通道是否暢通、延遲情況 |

### 8.2 狀態共享格式
```
[雙蜂狀態] [來源隊伍] [時間戳]
熵值: xxx（目標 < 0.1）
任務負載: xx 個任務（忙碌程度 xx%）
代理健康: 正常 / 異常（明細）
通道狀態: CHANNEL_OPEN / DEGRADED / CLOSED
```

## 九、雙蜂組健康檢查協定

### 9.1 健康檢查項目
雙蜂組健康檢查涵蓋以下項目：

| 項目 | 檢查內容 | 正常標準 |
|------|----------|----------|
| 雙隊運行狀態 | 兩隊是否同時運行 | 兩隊均運行中 |
| 熵值達標 | 兩隊熵值是否 < 0.1 | 兩隊熵值皆 < 0.1 |
| 通道暢通 | 協作通道是否正常 | 通道狀態 = OPEN |
| 5T 驗證通過率 | 最近 1 小時計數 | 通過率 100% |
| 任務完成率 | 最近 5 分鐘完成任務數 | 符合預期 |

### 9.2 健康檢查頻率
- **例檢**：每小時執行一次完整健康檢查
- **急檢**：當狀態異常時立即執行緊急檢查
- **喚醒檢**：雙蜂組喚醒時執行喚醒前健康檢查

### 9.3 健康檢查結果處理
- **全綠**：雙蜂組正常運作，繼續執行
- **單項異常**：針對異常項目執行修復流程
- **多項異常**：進入 TWIN_DEGRADED 狀態，指揮層介入
